## 更名方案：rpi → latent（脚本化全仓替换 + 分步验证）

原则：一条**带边界保护的替换脚本** + 每步可独立验证 + 全程在独立分支单 commit 内完成（git 一键撤销）。

### 为什么要边界保护（本方案的核心风险点）
盲目 sed 有两类必然改错的坑：
1. `rpi` 是英文单词 **warping / sharpie / carping** 等词的子串——直接 `s/rpi/latent/g` 会把无关单词改坏；
2. 更隐蔽的是 env 名：**所有 `*_API_KEY`（如 `ANTHROPIC_API_KEY`）都含子串 `PI_`**——若简单替换 `PI_` → `LATENT_`，17 家 provider 的 key 名全部损坏。

因此用 perl 负向后顾断言，只替换"标识符开头"的 rpi（前面不是字母/数字/下划线才命中），`rpi_ai`、`RPI_BIN`、`.rpi` 都会命中，而 `warping`、`ANTHROPIC_API_KEY` 里的子串绝不会命中。

### Step 0：盘点（只读）
- `git grep` 统计 `rpi`/`RPI`/`Rpi`/`PI_` 各自出现次数与分布，确认实际使用的 env 前缀（AGENTS.md 里同时出现 `PI_*` 注入和 `RPI_EDITOR`，需以代码为准逐一确认）；
- 列出特殊位置清单：bin 名、`.rpi/` 配置目录（含仓库自带的 `.rpi/` → `.latent/`，否则 skills/agents/settings 停止加载）、`--rpi-landlock-helper` flag、GitHub URL。

### Step 1：文本替换（一条脚本，只碰 git 跟踪文件）
```bash
git ls-files -z | xargs -0 perl -pi -e '
  s/(?<![A-Za-z0-9_])RPI/LATENT/g;
  s/(?<![A-Za-z0-9_])Rpi/Latent/g;
  s/(?<![A-Za-z0-9_])rpi/latent/g;
'
```
- `PI_*` env 前缀按 Step 0 盘点结果，用同样的后顾断言单独精确替换（确保 API_KEY 类不受影响，替换前后各 grep 一次对比次数）；
- 裸词 `pi`（指上游 pi 的所有文档引用）**不在替换范围**，保持原样。

### Step 2：目录改名（内容替换之后）
```bash
git mv crates/rpi-cli crates/latent-cli   # 9 个 crate 同理
git mv .rpi .latent
```
（Step 1 已把 Cargo.toml 的 `path = "crates/rpi-*"` 改写为 latent-*，mv 后正好对齐。）

### Step 3：全量验证（任何一步不过即停，review diff）
1. `git grep -i rpi` 残留检查（预期：0 处；上游 pi 的引用本就不含 rpi）；
2. `cargo build --workspace` + `cargo test --workspace` + `cargo clippy --workspace --all-targets` 全绿；
3. `cargo run -p latent-cli -- --mock "你好"` 走通全链路；
4. `cargo build --bin latent` 后跑 `tests/e2e` 冒烟子集（startup/ask_and_reply/fullscreen），验证 PTY 场景下 bin 名、HOME 内 `.latent/` 会话路径、`LATENT_BIN` 全部一致。

### Step 4：人工 review + 收尾
- 完整过一遍 `git diff`（重点：README/AGENTS/e2e harness），确认语义无误后，分支 `rename-latent` 上单 commit 收口，合回 main；
- 后续发布（GH Releases 流水线、install.sh、crates.io 按 `latent-ai → … → latent-cli` 依赖序 publish、仓库改名 hellolio/latent）作为独立任务在更名落地后进行，届时另列清单确认。

### 回滚保障
所有改动在分支单 commit 内；任何阶段发现问题 `git reset --hard main` 即可全量撤销。
