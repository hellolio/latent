# latent-web：网络搜索扩展 Rust 重实现方案

依据 `docs/web-search-principles-and-prompts.md`（下称"分析文档"），将 web-access 核心移植进 latent。已确认取舍：**四件套 + web_access**；**精选 5 家 provider**；**none + auto-summary**（省略 summary-review 浏览器 UI）；**新 crate latent-web**；**独立 web-search.json 配置**；**凭据支持明文/$ENV/!命令**；**权限全部 ReadOnly**；**摘要模型配置指定 + 回退主模型**。

## 1. 新 crate：`crates/latent-web`

分层对齐 latent-tools（仅依赖 `latent-agent`（Tool trait）+ `latent-ai`（Provider/Model）+ tokio/reqwest 等基础设施，**不依赖 latent-core/latent-cli**）。所有宿主能力通过 `WebDeps` 注入（仿 `SubagentDeps` 模式）：

```rust
pub struct WebDeps {
    pub provider: Arc<dyn latent_ai::Provider>,            // 摘要/answer 模式的 LLM
    pub resolve_model: ModelResolveFn,                  // "provider/model" -> Model
    pub current_model: Box<dyn Fn() -> Option<latent_ai::Model> + Send + Sync>, // 回退主模型
    pub tool_set_activator: Arc<dyn ToolSetActivator>,  // web_access 用（见下）
    pub notify_follow_up: Arc<dyn BackgroundNotifier>,  // includeContent 后台完成通知
    pub cwd: PathBuf,
    pub home: Option<PathBuf>,
}
```

对 latent-core 的两个解耦关键点：
- **`ToolSetActivator` trait**（latent-web 内定义，`async fn activate(&self, add: &[String]) -> Result<(), String>`）：web_access 需要调用 `AgentSession::set_active_tools_by_name`（session.rs:561），但不引 latent-core 依赖 —— trait 在 latent-web 定义，实现在 latent-cli/assembly.rs 里包一层 `Arc<AgentSession>`（Weak 引用，仿 subagent_parent_cell）。
- **`BackgroundNotifier` trait**：includeContent 后台抓取完成后通过 `agent.follow_up` 触发新 turn 通知，实现仿 subagent registry supervisor（registry.rs:82-96：等 idle → follow_up）。

## 3. 五个工具要点

1. **web_search**：参数照分析文档 §2.1 逐字（query/queries/numResults/includeContent/recencyFilter/domainFilter/provider/workflow/proxy）。多 query 用 `tokio::sync::Semaphore(3)` 并发，单 query 失败降级为该 query 的 error 字段；`Searching "..." (n/m complete)...` 进度走 `ToolUpdater`。结果组装（Provider 标注头、answer+Sources 格式、完整结果模式）用 prompts.rs 契约文案；有界输出 + 存 storage + 返回 responseId 检索指引。includeContent=true 时 spawn 后台抓全文，完成后经 `BackgroundNotifier` 通知。`workflow` 枚举为 `["none","auto-summary"]`（**偏离上游**：不含 summary-review，因 curator UI 省略）。
2. **get_search_content**：完整移植 responseId 检索、offset/limit 分页、findText 三模式。参数与文档一致（limit 上限 = maxInlineContentChars）。
3. **fetch_content**：三模式 `readable/raw/answer`（description 中的 FETCH_MODE_DESCRIPTIONS 逐字）。**省略** forceClone/timestamp/frames/model/auth/answerModel 参数（PDF/GitHub/YouTube/视频/浏览器 cookie 通道不做）；url/urls/prompt/mode/proxy 保留。answer 模式复用摘要模型链（summaryModel → 主模型）。
4. **source_check**：claim/queries/numResults/fetchContent/recencyFilter/domainFilter/provider/proxy；产出 ResearchArtifact JSON（结构照 source-check.ts:11-54）存入 storage，渲染格式照 §2.3。
5. **web_access**：空参数；description 逐字。执行时调 `ToolSetActivator` 把四个 web 工具加入激活集。

## 4. 装配与权限（latent-cli / latent-core 改动，最小化）

- **assembly.rs**：加载 web-search.json → 构造 `WebDeps`（provider/model 解析复用现有 subagent_resolver 同款；ToolSetActivator/BackgroundNotifier 用 session Weak cell 包装）→ `tools.extend(latent_web::create_web_tools(&deps))`（插在 assembly.rs:821 与 subagent 注册之间，使其进入候选池与 subagent tool_pool）。**默认懒激活**：构造 `active_tool_names` 时若 web 工具在候选集则默认只激活 `web_access`（settings `tools` 显式列出的用户配置优先）。
- **permission/types.rs `classify_tool`**：五个工具名加入 ReadOnly 分支（注释说明：无本地写副作用，缓存写专属目录；同 subagent 待遇）。
- 不改 latent-agent/latent-tools/latent-session。

## 5. 契约与测试

- **prompts.rs 契约测试**：逐条断言分析文档第二部分摘录的字符串常量逐字节一致（含标点与换行），作为回归基准。
- 单测：错误分类、结果数 clamp [1,20]、bounded 截断、findText fuzzy、storage TTL/LRU 修剪、SSRF CIDR 封锁、凭据三种来源解析与 redact。
- 手工验证：duckduckgo（零配置）真实搜索 → 多 query 并发 → responseId 分页/findText → fetch_content readable/answer → auto-summary（配 summaryModel 时）。

## 6. 已知交互与偏离说明

- latent loop 对 tool result 有 20k head/tail 截断（loop_.rs DEFAULT_TOOL_RESULT_MAX_CHARS）：web 默认 maxInlineContentChars 仍取上游 30k，检索指引在尾部可保留；文档中会注明此差异。
- 上游"零配置默认走 Exa MCP"不做（exa 走 key 通道），零配置兜底为 duckduckgo。
- 全部 provider 不可用时的兜底指引文案按我们 5 家 + duckduckgo 兜底改写（保持原文格式）。
