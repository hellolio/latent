允许 Plan 模式下 `cd` + 后续全只读的复合命令

## 背景
`cd /path && git status && git log --oneline -5 && file rpi` 在 Plan 模式被拒，根因是 `cd` 不在只读前缀表 `READONLY_PREFIXES`（crates/rpi-core/src/permission/shell.rs:16-120），`check_command` 在第一个 `&&` 处短路判非只读，Plan 模式下直接 Deny 不弹审批（engine.rs:166-169）。`cd` 本身无副作用——安全性由"其余段必须全部通过只读判定"保证，`cd` 到哪里都只影响只读命令看哪个目录。

## 改动

### 1. crates/rpi-core/src/permission/shell.rs
- 在 `READONLY_PREFIXES` 表中新增 `&["cd"]`（放在"零副作用命令"分组附近），附注释说明：cd 自身无副作用，放行它的前提是分段校验仍要求其余所有段只读；deny 规则（`approval.denyCommands`）否定优先，仍然可以显式禁掉 cd。

### 2. 同文件 `#[cfg(test)] mod tests` 新增用例
- 用户原始场景：`cd /Users/kin/Documents/10source/test && git status && git log --oneline -5 && file rpi` 判定通过；
- 单独 `cd /tmp` 通过；`cd ..` 通过；
- `cd /tmp && rm -rf x` 仍拒绝（非只读段一票否决不变）；
- deny 规则含 `cd` 时 `cd /tmp && git status` 拒绝（否定优先不变）；
- 既有用例（如 `pipelines_with_non_readonly_or_dangling_segment_fail`）不动，确认无回归。

## 验证
- `cargo test -p rpi-core`（重点 permission 相关）
- `cargo test --workspace` + `cargo clippy --workspace --all-targets` 全绿零警告（提交前硬门槛）
- 行为核对：Confirm/FullAccess 模式不受影响（该表只用于只读判定；Confirm 下非只读仍走 Ask 审批，cd 放行后反而少弹一次不必要的审批）
