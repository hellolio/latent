# latent 架构改造计划

## 前置结论（已核实源码）

任务清单 `docs/latent-architecture-fix-tasks.md` 中 4 个问题全部属实：
1. **Model/URL 配置**：`Model` 结构体字段齐全但 `ModelResolver` 只用 `latent-ai/src/provider.rs:76` 硬编码端点表；CLI 无 URL 入口；`latent-cli/src/main.rs:195` env-key 白名单在 resolve 前拦截自定义 provider；适配器内（`anthropic.rs:654`、`openai_completions.rs:791`）还有**第二道**白名单检查需一并处理。
2. **Session 仅内存**：`latent-session` 的 JSONL 持久化/加载/续聊已完整实现且有测试，但 `latent-cli/src/assembly.rs:176` 硬编码 `create_session(None)`。
3. **两套历史**：projection 完整但生产零调用；Agent 上下文只来自内存 `state.messages`。
4. **Overflow/Compaction 分裂**：`latent-core/src/session.rs:473-475` overflow 时直接砍内存 Vec（无摘要、无落盘）；`latent-session/compaction.rs` 完整管线只在测试里跑，`Summarizer` 无 provider 实现。

## 已确认的设计决策

- **配置位置**：全局 `~/.latent/` 为主，项目 `.latent/` 可覆盖（项目优先，与现有 `load_mcp_server_specs` 的读取顺序一致）；sessions 统一放 `~/.latent/sessions/`，header 记录 cwd。
- **apiKey 语义**：值优先按环境变量名解析，未命中时当字面 key 使用。
- **本次顺带加 `--continue`**（续聊最近 session）。
- **Compaction 摘要用当前会话的 provider/model**。

## Phase 1：Model / Provider / URL 配置体系

**新增配置加载（latent-core 新模块 `config.rs`）：**
- `models.json` 格式：`{ "providers": { "<id>": { baseUrl, api, apiKey, headers, compat, models: [...] } } }`，字段 camelCase，与 Pi 一致。
- 读取顺序：项目 `.latent/models.json` → 全局 `~/.latent/models.json`，同名 provider 深度合并（**项目覆盖全局**；provider 内 user override 与 built-in 合并，不要求重定义全部 model）。
- provider 级字段为默认值，model 级可 override（baseUrl/api/apiKey/headers/compat/reasoning/input/contextWindow/maxTokens 等）。
- `apiKey` 解析：env 名优先、未命中当字面值；缺失则不传 key（本地服务场景）。headers value 同语义。真实 key 不写入默认配置/测试/日志。
- `settings.json`：扩展现有加载逻辑，新增 `defaultProvider` / `defaultModel`（与 mcpServers、commandPrefix 并存）。

**扩展 ModelResolver（`latent-core/src/model.rs`）：**
- `create_model_resolver` 增加从配置加载的自定义 provider/model 注册；合并顺序：models.json 自定义模型 → built-in 端点表，覆盖已有 provider 的 baseUrl 时只改 URL 不动其 model 列表。

**CLI 改造（`latent-cli/src/main.rs`）：**
- 移除 `main.rs:195` 的 env-key 前置检查；credential 改为"解析具体 Model 后按其配置获取"，解析结果通过 `opts.api_key` 传入适配器（绕过适配器内白名单 fallback）。
- 适配器侧：`resolve_api_key` 对配置了 apiKey 的请求不再走白名单；无 key 的请求不发 Authorization 头、不报 setup_error。
- 参数：支持 `--provider <id> --model <id>` 与 `--model <provider>/<id>`；未指定时读 `settings.json` 的 defaultProvider/defaultModel，再没有才报错。

**测试**：合并逻辑、继承 override、apiKey env/literal 解析、custom provider 不再被拦截、custom base_url 生效（mock adapter 层面验证 URL 拼接）。

## Phase 2：Session 文件持久化

- `assembly.rs:176`：改为 `create_session(Some(path))`，路径 = `~/.latent/sessions/<session-id>.jsonl`（目录不存在则创建，latent-session 已支持）。
- 持久化覆盖现有全部 Entry 类型：Message（user/assistant/toolResult 经 SessionBridge 已自动 append）、ModelChange、ThinkingLevelChange、Usage 等在对应事件点补 append（沿用"逻辑事件完成后写入，不逐 token 落盘"原则；SessionManager 每次 append 已即时写盘+flush）。
- 新增 CLI 参数 `--continue`：列出 `~/.latent/sessions/` 最新文件，`create_session(Some(该文件))` 走已有的加载续聊路径。
- `--resume`/`--fork` 不做，但不动 `branch()`/`parent_session` 预留。

**测试**：四种模式跑完产生 JSONL；崩溃进程重启后 `--continue` 恢复完整历史。

## Phase 3：Session / Agent Transcript 统一

- 建立"Session = source of truth，Context = projection"：
  - 加载路径：session 文件 → `load_file` → `build_session_projection` → 构建 Agent 初始 `state.messages`（`--continue` 即走此路径）。
  - 一致性补齐：ModelChange、ThinkingLevelChange、Compaction、ContextEdit 等 entry 与 Agent 侧状态变更双向对齐（Agent 侧改状态时 append entry；启动时从 entry 恢复状态）。
- 不逐 token 重新 projection；Context 保持内存增量更新，但保证可随时从 Session 重建。

**测试**（对应文档验收 Test 1–3）：完整 run（user→assistant→tool call→tool result→assistant）落盘后，仅从 JSONL 重建的 context 与运行结束时 Agent context 一致；tool interaction 恢复正确。

## Phase 4：Overflow / Compaction 统一

- 删除 `latent-core/src/session.rs:473-475` 的 `drop_last_message` + `trim_oldest_messages` 砍半逻辑。
- 统一入口：`latent-core` 装配 `Summarizer` 的 provider 实现（用当前会话 provider/model 发摘要请求，复用 `run_compaction` 的 `SUMMARIZATION_PROMPT` 管线）。
- overflow 触发（`is_context_overflow` 命中）→ 调用 `run_compaction` → `SessionManager::append_compaction` 落盘 → 从 projection 重建 Agent context → 继续运行。保留现有 `overflow_recovery_attempted` 单次限制。
- 原始历史不删除（JSONL append-only 不变）；projection 已支持 Compaction 虚拟展开（`projection.rs:72`），复用。
- manual `/compact` 命令（interactive 模式）调用同一 compaction 实现。

**测试**：overflow → compaction → 落盘 → 重启 → projection 得到一致的压缩后 context；原始历史仍在文件中。

## 明确不做（与文档一致）

Permission System、MCP 动态更新、TUI 跨平台、Unicode、Subagent、OAuth、credential store、新 API adapter、provider catalog、大规模 crate 重构。发现相关问题只记录不扩大范围。

## 风险提示

- Phase 3/4 会触碰 latent-agent 的 `LoopState.current` 与 latent-core `AgentSession` 的核心不变量，改动集中在装配与恢复路径，不动 agent 循环状态机本身，以降低回归风险。
- 适配器去掉第二道白名单后，需保证内置 provider 行为不回退（已有测试 + 新增 mock 验证）。
